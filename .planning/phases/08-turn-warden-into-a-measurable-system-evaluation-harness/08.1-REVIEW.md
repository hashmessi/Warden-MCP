**Executed:** 2026-09-13  
**Objective:** Subject the evaluation framework to adversarial self-attack, stress testing, and vulnerability modeling before progressing to Week 2.

## 1. The Core Attack Questions & Real Findings

### Question 1: Can the tests produce false positives?
- **Finding:** **YES.** In `src/eval/scenarios/race-conditions.ts`, the approval race condition check contained:
  ```typescript
  const approvalRacePassed =
    finalApproval?.status === "approved" &&
    approvalSuccesses.length >= 1 &&
    approvalSuccesses.length + approvalFailures.length === approvalAttempts;
  ```
  If the row lock had failed and multiple concurrent approvers succeeded, `approvalSuccesses.length >= 1` would still evaluate to `true`, masking duplicate approvals.
- **Fix:** Hardened assertion to strictly require `approvalSuccesses.length === 1` and `approvalFailures.length === approvalAttempts - 1`.

### Question 2: Can a test pass while data is actually corrupted?
- **Finding:** **YES.** In `PostgresAdapter.restoreRecords`, snapshot records were queried without deterministic ordering:
  ```sql
  SELECT record_id, data FROM snapshots WHERE execution_id = $1 AND source_system = 'postgres'
  ```
  Under high vacuum or parallel query states, child rows (`user_activity`) were returned before parent rows (`users`), triggering foreign key violations (`23503`). Initially, errors inside the insert loop were logged to stderr but swallowed, leaving the database partially restored.
- **Fix:** 
  1. Added `ORDER BY id ASC` to snapshot restoration queries to preserve entity insertion topology.
  2. Modified `restoreRecords` to re-throw errors rather than swallowing them silently.

### Question 3: Can cleanup fail and leave evaluation artifacts?
- **Finding:** **YES.** Multiple leakage vectors were identified:
  1. `execution_steps` rows were never cleaned up because they lacked foreign key cascade constraints.
  2. `cleanupTestSubject` relied on subqueries against the `scans` table. Under heavy concurrency bursts (8 parallel agents), non-blocking scan writes dropped under PostgreSQL connection pool timeouts. As a result, `scans` had no record, causing `cleanupTestSubject` to bypass snapshot and step deletion, leaking hundreds of orphaned records.
- **Fix:** Enhanced `cleanupTestSubject` in `src/eval/seeder.ts` to inspect snapshots directly for the subject's `email` and `user_id` without coupling to the `scans` relation, guaranteeing 100% artifact reclamation.

### Question 4: Can the fault injector behave differently from a real failure?
- **Finding:** **YES.**
  1. `FaultProxy.reset()` had a typo (`failureRules.clear;` without parentheses), preventing failure rules from being cleared.
  2. `checkInterception` threw exceptions *pre-call*. In real distributed environments, failures occur mid-stream (e.g. half of the sessions deleted, then socket hangup).
- **Fix:** Corrected `failureRules.clear()`. Documented mid-stream failure implications in `docs/FAILURE_MODES.md`.

### Question 5: Are your tests deterministic?
- **Finding:** Initially no (flaky under concurrent bursts due to audit hash chain contention and foreign key restoration ordering).
- **Fix:**
  - Expanded `AuditLogger.appendLog` retry budget to 12 with exponential backoff and randomized jitter (`8 * 1.3^attempt + random(0, 30ms)`).
  - Enforced `ORDER BY id ASC` on snapshot restoration.
